## 2. Project purpose and engineering approach

TradingAgents produces an analyst-supported trading decision. A plausible final answer can still be misleading when an indicator uses too little history, an analyst's evidence is absent, a news retrieval event is not traceable, or usage is attributed to the wrong analyst. Our work addresses these concrete failure modes. O1 makes insufficient SMA history visible. O2 records a run manifest. O3 bounds the news context supplied to an analyst. O4 checks evidence before an authoritative rating is published. O5 distinguishes news retrieval outcomes and records private evidence. O6 reports per-analyst usage with explicit unknown values.

We treated each feature as a requirement with an observable acceptance condition. B maintained the selected machine-readable registry at `docs/req/requirements.yaml`; interface and test plans supplied the detailed boundaries for a batch. The feature owner proposed tests, a designated human reviewed them, A approved the agent's execution scope, and the coding agent worked inside that scope. The resulting PR was examined using offline tests, regression checks, CI and human review. This was an actual workflow with mistakes and rework, rather than a claim that a static policy file alone enforced it.

The design also separates *advice* from *authority*. A Portfolio Manager's proposed Buy is not automatically the rating that the application may publish. The O4 gate evaluates selected evidence and may change the effective result to REVIEW. Similarly, O1 refuses to present a partial-window mean as a valid 200-session SMA. In O6, missing token usage remains Unknown instead of becoming a misleading zero. These decisions use deterministic checks around the agent-generated content, because natural-language output is not a reliable enforcement boundary.

We kept retrieval behind the existing dataflows layer and preserved public Yahoo tool signatures. Shared files such as `cli/run.py` and `tradingagents/graph/trading_graph.py` needed coordinated integration, so C handled their production wiring and the feature owners supplied contracts and tests. This arrangement reduced simultaneous edits to the same files. It did not remove integration delays: the actual project showed that splitting requirements among people was not enough to define all cross-feature interfaces.

### 3.1 O1: a valid result rather than a plausible number

### 3.2 O2: provenance with explicit limits

O2 attempts one JSON manifest for a completed CLI run. It records run identity, allowlisted effective settings, a configuration fingerprint and artifact references. The CLI reserves a unique run directory; B's writer creates the manifest, and C integrated finalization after report-save handling. If the write fails, the analysis result and effective rating remain intact and the CLI warns that the manifest was not saved. Tests cover atomic writes, unknown or sensitive fields, path traversal, collision handling and Hold/REVIEW preservation.

A test that merely located one manifest did not prove that the finalization hook ran exactly once. B asked OpenCode to wrap the real hook with a spy, count calls, and still let the real writer produce the JSON. A later test also checked a relative `../outside.md` artifact path. These checks are better evidence than a picture of a plausible JSON file. B's historical Windows/Python 3.13.7 run recorded 36 focused passes at implementation commit `6b538cf`; the PR head after AI-use evidence had 11/11 CI checks. Those figures should not be combined with the newer six-gate CI count as though they came from one run. The manifest's fingerprint covers normalized identity and allowlisted configuration, not all external market data or model outputs.

## 4. Architecture and integration decisions

The selected architecture is an incremental extension to the inherited TradingAgents application. The repository's architecture blueprint, ADR, invariant register, trace matrix, memory design, permission model, runtime policy catalog and candidate evaluation table record the intended design and its alternatives. Their presence documents our decisions; a text file alone does not prove that a runtime permission guard or all quality claims are enforced. The final report should refer to the versions actually merged into the submission tree, not to an earlier handoff ZIP.

Our main components remain dataflows and vendor adapters, the agent/Graph execution path, the CLI, reports, deterministic validators, offline tests, and the CI workflow. O1 is placed at the Yahoo data validity boundary. O2 writes evidence after a completed run. O3 prepares bounded news context for the Sentiment Analyst. O4 separates an agent's suggestion from the authoritative rating at publication. O5 records retrieval evidence in the reserved run scope. O6 observes selected analyst execution and displays truthful completeness. These placements were chosen to preserve existing public interfaces and keep assertions close to the boundary where a bad result could otherwise become visible.

C's experience showed a weakness in our original planning. We assigned individual requirements early, but we did not map every dependency among the new features. O2 and O5 both needed the run directory; O4, O6 and O2 touched Graph or CLI execution; reports could expose pre-gate text. Developers spent time confirming signatures, execution order and ownership. The subsequent integration contract and C-owned shared-file review reduced the risk of conflicting edits. In a future sprint, we would write the dependency map and minimum interface contracts immediately after selecting the feature set, before parallel implementation.

The architecture material includes a layered context design for an AI coding agent and a policy for retained state, but the team's recorded workflow is narrower than a claim of perfect automated enforcement. The agent read standing instructions, requirements, a bounded task, relevant source and prior state; students then reviewed its proposed plan and output. Context compaction and re-injection are design policies in the architecture documents. We do not claim independent measurement that every OpenCode turn had exactly the designed token budget or layer order. The permission matrix documents approved paths; it is not evidence of operating-system or OpenCode path enforcement. Human review, CI and GitHub protection were separate, observable controls.

## 6. Verification and quality controls

Verification used three complementary levels. **Structural checks** covered requirements Schema, imports and dependencies, type and Ruff checks, contract/API/security/permissions governance checks, and clean installation. **Behavioral checks** included deterministic O4 and O5 semantic cases and each feature's offline assertions. **Regression checks** reran the existing application suites in multiple Python environments. These gates help detect different classes of failure; no single green status proves that every requirement, external provider or live trading path has been tested.

F's CI handoff distinguishes six *categories* of gates from 17 named PR checks. The categories were Test Approval, Static Analysis, Requirements Schema, Semantic Evaluation, Regression and AI-use Log. The 17 contexts included four Python matrix jobs, clean-install smoke, Ruff, type check, dependency audit, four governance checks, requirements schema, two semantic checks, test approval and AI-use log. On a `main` push, the PR-only Test Approval and AI-use checks may be skipped; skipped is not the same as passed. Historical `main@252fe31` push run `44988759013` had 15 successful jobs and two PR-only skips. Its Python 3.11 job reported 2,126 passes, one skipped, one deselected and 100 passing subtests. These results belong to that commit, not automatically to the final freeze.

Passing CI is only one part of a merge control. A and F set a classic protection rule for `main`: required checks, one approving review, dismissal of stale approvals on new commits, and no bypass for administrators. Configuration screenshots were archived, with hashes; F did not claim an independent administrator API readback. A temporary PR #41 provided observed behavior: all 17 checks could pass while the missing review still blocked merge; a controlled Schema fault made Schema and four related regression checks fail and stale review disappear; after normal repair, 17/17 success and a fresh valid review restored merge eligibility. The experiment was closed without merging. E3 and some other possible protection behaviors were not exercised, so the report describes the verified cases rather than universal enforcement.

The CI evidence also exposed a practical limitation. An intentional Schema fault did not isolate to one red job, because the regression jobs used the same invalid requirement file. The team recorded the correlated failures as such and repaired the real file in a follow-up commit. This is better evidence than forcing a misleading single-job demonstration. Review and check-state transitions were observed at specific commits; they should not be copied to a later commit without rerunning the relevant checks and reviews.

## 7. Process quality, change and defect evidence

Requirements evolved as ambiguous behavior became testable. The TC-17 correction fixed a trace link. For final reporting, we instead state the symptom, tested SHA, correction and remaining boundary for each.

We improved the process in four ways. First, plans identified exact files and test nodes before implementation. Second, shared integration was routed through one owner while feature owners supplied contracts and tests. Third, offline deterministic fixtures reduced dependence on credentials and live market changes. Fourth, PR evidence tied tests, approvals and AI-use logs to specific versions. The cost was additional coordination and repeated review after revisions. C's reflection and the S5 closure show that the team would benefit from an earlier integration map and smaller per-batch evidence checklist. These improvements describe how we worked; they are not a claim that the process was optimal or fully automated.

### 8.3 Risks we accepted and follow-up work we declined

Our most important accepted risk is that deterministic offline verification uses controlled inputs. It makes boundary conditions reproducible, but it cannot establish that every live provider response, model message or market condition is handled identically. We chose to preserve public APIs and focus on specific safety and provenance faults instead of rewriting TradingAgents. This made the changes reviewable within the course timetable but left the other vendor routes and some live paths outside our claims. It also means that a successful offline result must be described with its fixture and tested code revision.

The team also accepted that governance evidence was partly procedural. A permission document can say which files an agent should modify, and the students can compare the PR diff to that scope. Unless the operating system or agent runtime actually applies the matrix, the document alone is not an enforcement mechanism. CI and GitHub branch protection provided separate checks. The temporary PR tested important blocking and recovery behavior, while E3 and some administrator/API readback questions stayed unverified. We kept the difference visible rather than converting a plan into a claim of machine enforcement.

Finally, the S6 performance extension had a concrete failed measurement. Continuing solely to obtain a green number would have risked consuming more time while changing the already reviewed S5 delivery. The team stopped it and kept the failure in the report. The useful outcome is a clear boundary: the final product includes the S1–S5 news improvements, while T17 performance remains future work requiring its own design, measurement and review. This decision is part of the engineering process, because scope control includes stopping work that has not met its acceptance criterion.
